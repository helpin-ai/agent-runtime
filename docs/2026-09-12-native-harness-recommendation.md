**Original recommendation, retained as audit context rather than the current implementation plan: make native_sdk the primary harness for Agent Runtime, including coding and review.**

Research date: 2026-09-12. This is an architecture recommendation and source audit, not an implementation or a production incident diagnosis. No runtime configuration was changed.

Concentrate new harness engineering on native_sdk. Keep Codex temporarily as an explicitly selected compatibility option and a quality benchmark while native coding and review pass acceptance gates. Keep separate coding and review profiles, contexts, permissions, and evaluation criteria within the shared harness. Sharing the execution engine does not require sharing the writer's conversation with the reviewer.

The desired ownership is one runtime-owned conversation/tool loop, one durable run model, one approval system, and one workspace execution interface, with provider-specific model and authentication adapters. OpenAI API access and ChatGPT/Codex subscription access should be distinct connection types. Consolidation will reduce integration state machines; it will also make this team responsible for maintaining coding quality, context handling, process execution, and provider compatibility.

**The reported failure has a concrete architectural explanation.** The error `thread/resume failed (-32600): no rollout found for thread id ...` means the responding Codex server cannot resolve the stored history required for that resume. It does not establish a model failure or an authentication failure.

| Evidence in this integration | Implication |
| --- | --- |
| [codex_session.go](/root/agent-runtime/internal/runtime/codex_session.go:30) saves thread ID, path, home, and pending interaction metadata as database artifacts. | Database persistence protects the pointer, not the underlying Codex history. |
| [codex.go](/root/agent-runtime/internal/runtime/codex.go:348) defaults the per-run home to a directory beneath the OS temporary directory. | A new worker may create the same directory name with none of its former contents. |
| [codex.go](/root/agent-runtime/internal/runtime/codex.go:562) resumes by thread ID and returns lifecycle errors directly. `ThreadPath` is recorded but not supplied on this resume path. | Retry does not restore missing history. Supplying a path would still require the file to exist. |
| [Production worker manifest](https://github.com/helpin-ai/gitops/blob/main/agent-runtime/prod/worker-deployment.yaml) declares two replicas and no persistent volume mount. | The deployment at the time did not make local Codex history portable between workers or pod replacements. Verify the current overlay before relying on this historical finding. |
| Every execution starts a new app-server process, and the adapter closes it afterward. | Process-local pending requests and terminal sessions cannot be assumed to survive a human pause. |

The most likely failure class is database state outliving worker-local Codex state. Confirm it with the original and resumed worker identity, effective Codex home, rollout existence, first-turn history, and pod restart history. Do not log token contents.

There is another relevant case: pinned Codex explicitly tests that a thread ID can exist before its first user message materializes a rollout; resuming then produces this same error. Check whether the failed run ever successfully started its first turn before diagnosing a lost volume. See the pinned [unmaterialized-thread regression test](https://github.com/openai/codex/blob/e363b08c9175ac1cbe5893615dd2cb9ddf95043b/codex-rs/app-server/tests/suite/v2/thread_resume.rs#L315).

The July [approval-resume investigation](/root/agent-runtime/docs/prd/2026-07-08-codex-resume-approval-hang.md) describes a related process-lifecycle mismatch. Its proposed bounded replay fallback is now visible in the implementation; the document is historical evidence, not proof that the old hang remains unfixed.

For the remaining Codex bridge, add a distinct missing-history failure category and recovery route. If history is still available, restore version-compatible session storage to the assigned execution environment. If it is lost, reconstruct a new run from durable user instructions, artifacts, repository state, and recorded outcomes, with clear provenance. Do not silently erase the thread ID and present a fresh run as a lossless resume; uncertain side effects must be reconciled first. Worker affinity alone does not survive pod loss.

Do not build the production fix around `thread/resume.history`: the pinned [protocol definition](https://github.com/openai/codex/blob/e363b08c9175ac1cbe5893615dd2cb9ddf95043b/codex-rs/app-server-protocol/src/protocol/v2/thread.rs#L324) explicitly labels it unstable and reserved for Codex Cloud. Current [official app-server documentation](https://developers.openai.com/codex/app-server) also describes resume as reopening stored state; a thread ID is not a portable transcript.

**Native already contains much of the required harness.** It is a custom Go execution loop using Eino model adapters, not merely a thin SDK invocation. Preserve the existing assets:

- OpenAI Responses, Anthropic, and OpenRouter provider paths; streamed assistant/tool events and usage accounting.
- Tool allowlists, app-scoped registration, MCP integration, native human input, approval reconciliation, review checkpoint interactions, plans, and explicit completion contracts.
- Read/write/edit/patch, repository search, symbol listing/reading/tracing, Git and repository lifecycle tools. The patch tool already accepts the familiar `*** Begin Patch` format.
- Parallel execution for batches containing only non-mutating tools. A blanket “native needs parallel tools” recommendation would be inaccurate.
- Managed context compaction with complete call/result groups, retained recent context, skill protection, optional human anchors, usage budgets, durable state/journal tables, and conservative interrupted-tool recovery.
- Shared workspace preparation, branch synchronization, finalization, and host-owned business operations.

The provider replay issue is particularly consequential for a long coding session. Native should not collapse every provider's conversation into text plus function calls. OpenAI's [reasoning documentation](https://developers.openai.com/api/docs/guides/reasoning) describes preserving replayable output items, including encrypted reasoning, in stateless operation. Add provider-tagged opaque state rather than attempting to display or synthesize private reasoning. Anthropic thinking/signature metadata needs equivalent preservation if thinking is enabled. Eino may remain useful; replace a lossy adapter boundary where necessary, not the entire orchestration stack by default.

**Device login should be ported as a connection capability, together with its transport.** The existing encrypted database token store is useful infrastructure, but its `Promote` operation unconditionally upserts an opaque auth file. Its scope is app/tenant/provider/auth-mode, without a separate connection/account identity. Login sessions live in an in-process map. Those are concrete limitations for multiple users, connections, and workers. See [auth persistence](/root/agent-runtime/internal/runtime/codex_auth.go:46).

Implement the following as one bounded provider project:

1. A connection record scoped by trusted app, tenant, owner, provider, and connection ID. Store account identity, token expiry, encrypted token material, version, and status. Explicitly distinguish API-key billing from subscription access.
2. A persisted device-login attempt with start/poll/cancel/expiry states and a worker lease. Preserve the current user-facing code/link experience. Completion and cancellation must remain correct when another API replica receives the request.
3. A single refresh owner per connection across workers, with a lease or lock spanning refresh and a version-checked token update. Re-read after acquiring ownership; prevent stale writers from replacing rotated tokens. Handle revocation and reconnect deliberately.
4. A dedicated Codex Responses transport: correct endpoint, account headers, model capability checks, streaming requirements, supported request parameters, terminal-event validation, quota feedback, and replayable opaque reasoning state. Do not point the ordinary API-key adapter at a different URL and assume equivalent behavior.
5. Explicit logout and migration of existing encrypted credentials where scope and account identity can be established. Do not silently adopt a developer's local Codex login or use one tenant's connection for another.
6. Provider-neutral API/SDK/UI connection status, retaining compatibility aliases for existing Codex-auth consumers during migration. Update host configuration, capabilities, billing display, and support diagnostics together.

Codex's [device flow implementation](https://github.com/openai/codex/blob/e363b08c9175ac1cbe5893615dd2cb9ddf95043b/codex-rs/login/src/device_code_auth.rs) provides the concrete request-code, bounded polling, PKCE exchange, and token-persistence sequence. The [official authentication guide](https://developers.openai.com/codex/auth) documents device login and recommends API keys for automation. That is a reason to keep API-key automation independent of subscription-login rollout, not a claim that native subscription access is impossible.

OpenCode's [Codex plugin](https://github.com/anomalyco/opencode/blob/95daf90670b7c039c436c85537da5fbfe2205b41/packages/opencode/src/plugin/openai/codex.ts) demonstrates direct integration: device/browser OAuth, refresh, account headers, and routing to the Codex Responses endpoint. Its in-process refresh promise is a useful pattern but is insufficient for our multi-worker deployment.

Hermes separates [Codex authentication](https://github.com/NousResearch/hermes-agent/blob/3e09e5a15f43e7253abaf4760f0487fece39ff93/hermes_cli/auth_codex.py), [Responses transport](https://github.com/NousResearch/hermes-agent/blob/3e09e5a15f43e7253abaf4760f0487fece39ff93/agent/transports/codex.py), and response conversion. It preserves Codex reasoning items and normalizes provider request behavior. These implementations demonstrate feasibility; they do not establish a permanent endpoint compatibility guarantee or universal account eligibility. Validate the intended supported account/workspace path before general release.

**Migration should proceed through measurable gates.**

First, contain the existing incident class: improve missing-history diagnosis and recovery, verify actual deployed persistence, and preserve recoverable existing runs. Freeze optional bridge expansion while continuing necessary reliability fixes.

Next, make native durability independent of compaction, secure and persist workspaces, preserve provider replay state, wire reasoning settings, expose existing patch/edit tools, and provide usable command processes. Extract review workflow guards from Codex into shared runtime policy. Build the provider connection/device-login project alongside this work; API-key evaluations can start earlier.

Then run paired evaluations on isolated copies of the same repository commits. Compare the same model, effective reasoning settings, task, and budget wherever both paths support them. Compare API-key routes separately from subscription routes. Use real Go/TypeScript/Python tasks: a small bug fix, a multi-file refactor, failing-test repair, a dependency installation/build, a large-file change, nested repository instructions, a long task requiring compaction, and a visual task if screenshots matter. Review cases need known defects and clean changes to measure missed issues and false positives.

Measure successful verified patches, test results, review precision/recall, human intervention, resume success, duplicate mutations, p50/p95 completion latency, model/tool rounds, token usage, and billed cost where available. For subscription routes, keep token usage and quota separate from API-dollar estimates. Publish failures by category, not just one success percentage.

Acceptance tests must include worker replacement after edits and during approval; tool success followed by a crash before outcome persistence; interrupted streams; repeated resume delivery; expired access tokens; simultaneous refresh on two workers; a terminal command lasting over two minutes; and compaction preserving user constraints and provider replay validity. No harness should “recover” by silently dropping an uncertain write.

Roll out a native review canary in isolated workspaces and a narrow coding canary, then expand only after the agreed quality and recovery gates pass. Read-only review policies still need a writable disposable test environment if the reviewer runs builds or tests. Update Helpin presets and reconciliation, runtime registration, SDK contracts, frontend connection/review behavior, deployment capabilities, and usage accounting together. Existing active Codex runs should drain on their recorded engine or use an explicit recovery migration; do not change engine identity underneath their checkpoints.

Retire the compatibility bridge when native demonstrates comparable task/review quality and better operational reliability on the workloads you actually run. The recommendation is to fund one harness as the product foundation now, while using evidence to choose when each workload moves.
